# 第一章 项目背景与建设目标

## 1.1 项目背景

随着大语言模型技术的发展，AI 应用逐渐从简单的问答系统向能够自主规划、调用工具和执行复杂任务的 Agent 系统演进。

传统的软件自动化系统主要依靠预先定义的流程执行任务，具有执行路径明确、结果可预测、过程容易控制等优点，但难以处理需要动态判断和自主决策的复杂任务。

Agent 系统则能够根据任务目标动态选择工具、调整执行策略，但同时带来了新的工程问题：

1. Agent 执行过程具有不确定性，难以保证执行结果。
2. 模型调用和工具执行可能耗时较长，容易受到网络和外部服务影响。
3. 多步骤任务需要保存中间状态，否则服务异常后可能需要重新执行。
4. 多个 Agent 或任务节点之间存在复杂的依赖关系。
5. 外部 API 调用可能失败，需要合理设计重试和幂等机制。
6. 涉及重要操作时，需要引入人工审批。
7. Agent 执行过程缺乏统一的监控、追踪和成本管理。

因此，单纯依靠 Agent 框架不足以构建可靠的企业级 AI 应用。

FlowPilot 希望解决的核心问题是：

**如何将具有不确定性的 Agent 执行能力，融入一个可靠、可观测、可恢复的后端任务执行系统？**

## 1.2 项目定位

FlowPilot 是一个面向复杂业务任务的智能工作流与 Agent 协同执行平台。

平台通过传统工作流引擎管理确定性任务，通过 Agent Runtime 处理需要动态规划和智能决策的任务，并利用统一的任务管理、持久化、消息调度和异常恢复机制保证整体执行可靠性。

核心设计理念：

- 确定性流程由 Workflow Engine 控制。
- 不确定性决策由 Agent Runtime 处理。
- 长时间任务由异步任务系统调度。
- 执行状态由持久化机制管理。
- 关键操作由人工审批控制。
- 执行过程通过统一的可观测系统追踪。

## 1.3 项目目标

### 后端工程目标

构建一个具备以下能力的后端系统：

1. 多用户身份认证与权限管理。
2. 工作流定义、版本管理与发布。
3. DAG 任务依赖解析。
4. 任务异步调度和并行执行。
5. 消息可靠投递与消费。
6. 任务幂等与重复执行控制。
7. 任务超时、失败重试和故障恢复。
8. 执行日志与状态追踪。
9. 多用户任务隔离与并发控制。
10. 实时执行状态推送。

### Agent 工程目标

构建具备以下能力的 Agent 执行模块：

1. 基于 LangGraph 构建 Agent 工作流。
2. 支持模型调用与结构化输出。
3. 支持动态 Tool Calling。
4. 支持 Agent 状态持久化。
5. 支持任务中断与恢复。
6. 支持人工介入。
7. 支持 Agent 执行过程追踪。
8. 支持 Token 消耗与调用成本统计。

## 1.4 项目非目标

为了避免过度设计，第一版明确不实现：

- 通用低代码平台。
- 完整替代 n8n、Dify 的工作流产品。
- 通用 Agent 市场。
- 自研大语言模型。
- 自研向量数据库。
- 自研消息队列。
- 完整的 Kubernetes 调度系统。
- 多 Agent 自由协商与无限递归委派。

项目重点是后端执行基础设施与 Agent 工程化，而不是追求功能数量。

# 第二章 竞品与技术生态调研

## 2.1 n8n

n8n 是一个成熟的工作流自动化平台，提供可视化工作流编排和大量第三方服务集成能力。

其核心特点：

- 可视化节点编排。
- 丰富的外部服务集成。
- 支持条件判断和循环。
- 支持 Webhook 和定时触发。
- 支持 AI 节点和 Agent 工作流。
- 支持通过队列模式扩展执行能力。

其队列模式采用主实例与 Worker 分离的架构，由 Redis 负责队列调度，数据库负责持久化执行数据。

**值得借鉴：**

1. 控制面与执行面的职责分离。
2. Worker 水平扩展。
3. 异步任务执行。
4. 工作流执行记录。

**FlowPilot 的差异化方向：**

不追求通用自动化集成能力，而是聚焦长时间运行的 AI 业务任务，重点研究任务状态一致性、Agent Checkpoint 和跨服务故障恢复。

## 2.2 Dify

Dify 是面向 LLM 应用开发的平台，提供 Workflow、Chatflow、知识库、模型管理和 Agent 等功能。

主要特点：

- 可视化 LLM 工作流。
- RAG 知识库。
- Agent 节点。
- 条件分支和并行执行。
- Human Input 人工介入节点。
- 模型供应商集成。

Dify 已经具备较完善的 AI 应用工作流能力。

**值得借鉴：**

1. AI 节点与普通业务节点结合。
2. 人工介入机制。
3. 工作流执行可视化。
4. 模型配置与工具管理。

**FlowPilot 的差异化方向：**

不重复建设知识库和模型管理平台，而是重点关注跨服务任务调度、任务生命周期管理、执行恢复以及 Java 后端与 Agent Runtime 的协同。

## 2.3 LangGraph

LangGraph 是基于图结构构建有状态 Agent 工作流的框架。

主要特点：

- State Graph。
- 条件边与并行执行。
- Checkpoint 持久化。
- Interrupt 中断机制。
- Human-in-the-loop。
- 执行状态恢复。

LangGraph 的 Persistence 机制能够保存 Agent 执行状态，支持在中断后恢复执行。

**值得借鉴：**

1. Agent 状态管理。
2. 执行过程持久化。
3. 动态中断和恢复。
4. 工具调用流程管理。

**FlowPilot 的差异化方向：**

LangGraph 主要负责 Agent 内部执行图，而 FlowPilot 负责整个业务任务的生命周期管理。

两者不是替代关系，而是上下层关系。

## 2.4 Temporal

Temporal 是值得重点研究的竞品。

它提供 Durable Execution（持久化执行）能力，能够让工作流在进程崩溃、服务重启和长时间等待后继续执行。

核心机制包括：

- Workflow。
- Activity。
- Event History。
- Replay。
- Retry Policy。
- Signal。
- Timer。
- Worker。

Temporal 的重要设计思想是通过持久化事件历史恢复工作流状态，而不是单纯依赖进程内存。

**值得借鉴：**

1. 执行状态与事件历史分离。
2. 工作流恢复机制。
3. Activity 独立重试。
4. 长时间等待和外部信号。
5. 确定性工作流设计。

**FlowPilot 的差异化方向：**

不试图重新实现 Temporal 的完整 Durable Execution 能力。

第一版采用数据库持久化、消息队列调度和任务状态机，实现一个范围受控的 DAG 执行引擎，并重点研究 Agent Checkpoint 与业务任务状态之间的协同。

## 2.5 Kestra

Kestra 是面向数据、基础设施、业务流程和 AI Agent 的工作流编排平台。

其新版本已经提供：

- LLM Tasks。
- AI Agent Tasks。
- RAG 工作流。
- MCP 集成。
- Worker 调度。
- 执行日志与结果追踪。

这说明通用工作流平台与 AI Agent 的融合已经是成熟的发展方向。

**值得借鉴：**

1. 声明式工作流定义。
2. Worker 执行模型。
3. AI 节点与普通任务统一编排。
4. 执行结果与日志管理。

## 2.6 竞品综合对比

| 产品 | 核心定位 | 工作流 | Agent | 持久化恢复 | 主要优势 |
|---|---|---|---|---|---|
| n8n | 自动化平台 | 强 | 支持 | 支持 | 丰富的集成生态 |
| Dify | LLM 应用平台 | 强 | 支持 | 支持相关机制 | AI 应用开发 |
| LangGraph | Agent Runtime | 图执行 | 核心能力 | Checkpoint | 有状态 Agent |
| Temporal | Durable Execution | 强 | 通过集成支持 | 核心能力 | 可靠任务执行 |
| Kestra | 通用编排平台 | 强 | 原生支持 | 执行持久化 | 多领域任务编排 |
| FlowPilot | AI 任务执行平台 | 核心能力 | 核心能力 | 重点建设 | 后端任务治理与 Agent 协同 |

## 2.7 竞品调研结论

经过调研，FlowPilot 不应该将以下内容作为创新点：

- 支持 DAG。
- 支持多个 Agent。
- 支持人工审批。
- 支持 RAG。
- 支持异步执行。

因为这些能力已经在不同程度上被现有产品实现。

真正值得重点建设的是以下组合：

1. Java 业务任务系统与 Python Agent Runtime 的跨服务协同。
2. 业务任务状态与 LangGraph Checkpoint 的一致性管理。
3. 基于数据库状态机的任务恢复和消息重复消费控制。
4. Agent 节点的超时、重试、成本预算与执行隔离。
5. 工作流级别的执行审计和完整追踪。

这些能力将构成 FlowPilot 的主要技术特色。

# 第三章 产品设计与业务场景

## 3.1 核心业务场景

第一版不开发通用工作流市场，而是选择一个真实业务场景作为完整的产品入口。

确定为：

**开源软件项目智能技术尽调。**

用户提交一个 GitHub 项目地址，平台自动分析项目的技术情况，并生成结构化的技术尽调报告。

### 用户输入示例

```text
请分析：

https://github.com/example/project

分析要求：

1. 项目基本信息。
2. 最近 30 天的提交情况。
3. Issue 和 Pull Request 活跃程度。
4. 主要依赖及其安全风险。
5. 最近版本更新情况。
6. 项目维护活跃度。
7. 潜在技术风险。
8. 是否适合用于生产环境。
```

注意：以上 URL 仅为输入格式示例，不代表真实项目。

## 3.2 业务执行流程

第一阶段：任务创建。

- 用户提交项目地址。
- 后端验证输入参数。
- 创建业务任务。
- 生成唯一 taskId。
- 将任务持久化。
- 发布执行事件。

第二阶段：数据采集。

并行执行：

- 项目基本信息获取。
- Commit 数据获取。
- Issue 数据获取。
- Pull Request 数据获取。
- Release 数据获取。
- 依赖信息获取。

第三阶段：数据分析。

对采集结果进行：

- 数据清洗。
- 统计分析。
- 时间趋势分析。
- 风险指标计算。

第四阶段：Agent 智能分析。

Agent 根据结构化数据完成：

- 技术架构分析。
- 项目维护状况分析。
- 潜在风险分析。
- 生产环境适用性评估。

第五阶段：人工审核。

用户可以：

- 确认分析结论。
- 修改部分结论。
- 要求补充分析。
- 驳回报告并重新生成。

第六阶段：报告生成。

生成结构化 Markdown 或 HTML 报告，记录数据来源和分析时间。

## 3.3 核心业务闭环

```text
用户提交项目
      |
      v
创建分析任务
      |
      v
异步任务调度
      |
      v
并行数据采集
      |
      v
数据处理与统计
      |
      v
Agent 智能分析
      |
      v
人工审核
      |
      v
生成技术报告
      |
      v
任务完成
```

所有执行阶段均需要记录状态、日志、输入输出和执行时间。

# 第五章 非功能需求

## 5.1 可靠性

系统需要保证：

- 任务状态持久化。
- 消息重复消费不会导致重复业务副作用。
- Worker 异常退出后能够识别遗留任务。
- 外部 API 调用具备超时和重试策略。
- Agent 执行失败能够保留必要的诊断信息。

## 5.2 可扩展性

系统应支持：

- 增加 Worker 实例。
- 扩展新的工作流节点。
- 扩展新的 Agent。
- 接入不同的大模型供应商。
- 接入新的外部数据源。

## 5.3 安全性

系统需要考虑：

- JWT 身份认证。
- 用户数据隔离。
- API 密钥保护。
- 外部 URL 校验。
- SSRF 防护。
- Agent 工具调用权限控制。
- 敏感操作人工审批。
- 防止模型提示词注入导致越权操作。

尤其需要注意：用户提交 GitHub 地址后，后端会主动访问外部资源，因此必须限制目标域名、协议、重定向和内网 IP 访问。

## 5.4 可观测性

每次任务执行应具有唯一的 Trace ID。

需要能够追踪：

```text
Task
  |
  +--- Workflow Execution
          |
          +--- Node Execution
          |
          +--- Agent Execution
                  |
                  +--- LLM Call
                  |
                  +--- Tool Call
```

# 第六章 项目技术原则

## 6.1 系统分层

采用双服务架构：

Java Backend：

- 用户体系。
- 工作流管理。
- 任务生命周期。
- DAG 调度。
- 消息管理。
- 执行记录。
- 权限控制。

Python Agent Service：

- Agent Runtime。
- LangGraph。
- LLM 调用。
- 工具执行。
- Checkpoint。
- Agent 内部状态管理。

## 6.2 数据一致性原则

MySQL 是业务任务状态的权威数据源。

Redis 主要承担缓存和短期协调职责。

RabbitMQ 负责异步消息传递。

LangGraph Checkpoint 负责 Agent 内部执行状态持久化。

不同存储之间不假设存在天然的分布式事务。

通过状态机、幂等键、事务 Outbox 和恢复扫描机制实现跨服务最终一致性。

## 6.3 执行语义

系统不宣称端到端 Exactly Once。

第一版采用：

- 消息至少一次投递。
- 消费端幂等。
- 节点执行记录。
- 业务副作用去重。
- 可恢复任务状态。

对于不能安全重试的外部操作，必须使用幂等键或人工确认机制。

## 6.4 开发原则

1. 优先保证核心链路可运行。
2. 不为了微服务而拆分过多服务。
3. 不为了展示技术而引入不必要的组件。
4. 每个复杂机制必须有对应的故障场景。
5. 所有性能指标必须通过实际测试得到。
6. 所有技术选型必须有明确的理由。

# 第八章 项目差异化总结

FlowPilot 不以通用工作流编排功能作为核心竞争力。

项目重点研究三个方面：

### 1. 业务任务与 Agent 状态的协同管理

解决 Java 任务系统与 LangGraph 执行状态之间的关联、同步和恢复问题。

### 2. 面向长时间运行任务的可靠执行

解决异步调度、消息重复投递、Worker 故障、任务恢复和幂等问题。

### 3. 确定性工作流与不确定性 Agent 的融合

让传统工作流控制任务边界，让 Agent 在受约束的范围内进行自主决策。

最终目标：

构建一个具有完整后端工程能力、可追溯执行过程和可靠 Agent Runtime 的智能任务执行平台。
